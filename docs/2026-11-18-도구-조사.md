# GitHub의 AI 개발 도구 조사 (2026-11-18)

devkit을 다시 설계하기 전에, GitHub에 올라와 있는 AI 개발 도구들이 무엇을 어떻게 하는지 훑어본 기록이다.

## 어떻게 찾았나

- GitHub 검색 23가지(스킬 묶음, 명세 기반 개발, 코드 지도, 테스트, 보안, 기억, 여러 AI 동시에 돌리기 등)로 471개를 모았다.
- 그중 개발 과정과 관련 있는 40여 개를 골라 읽었다.
- 읽은 깊이는 다르다.
  - 스킬 본문을 읽음: mattpocock/skills (39개 중 19개), addyosmani/agent-skills (25개 중 15개), garrytan/gstack (76개 중 15개), gsd-build/get-shit-done (명령·역할 문서 7개)
  - 전체 파일 목록은 넷 모두 확인했다. 읽지 않은 스킬은 이름과 한 줄 설명만 보았다.
  - 이 PC에 깔려 있어 이미 아는 것: obra/superpowers
  - 소개 문서(README)만 읽음: 나머지 31개
- 별 수는 조사한 날 기준이고 천 단위로 줄여 적었다.

## 1. 거의 모든 도구가 똑같이 하는 것

서로 다른 사람이 만들었는데 같은 결론에 닿은 것들이다. devkit도 여기서 벗어날 이유가 없다.

| 공통점 | 그렇게 하는 도구 |
|---|---|
| 묻기 → 글로 적기 → 작게 쪼개기 → 만들기 → 검토 → 배운 것 남기기, 이 순서로 간다 | superpowers, agent-skills, BMAD, spec-kit, OpenSpec, compound-engineering, Trellis, ECC, GSD |
| 만들기 전에 이미 있는 것부터 찾는다 | ponytail, gstack, GSD, agent-os, Trellis |
| 만든 AI가 아닌 "처음 보는 눈"에게 검토를 맡긴다 | Google EGM, mattpocock, cloudflare, agent-skills, compound-engineering, ECC |
| 꼭 지켜야 하는 것은 글로 부탁하지 않고 자동 장치로 막는다 | tdd-guard, planning-with-files, alibaba open-code-review, impeccable, mattpocock |
| 대화가 끊겨도 이어지도록 진행 상황을 파일에 둔다 | planning-with-files, beads, compound-engineering, Trellis, GSD, mattpocock |
| 일의 크기에 따라 절차를 줄인다 (작은 일에 전부 돌리지 않는다) | BMAD, spec-kit, OpenSpec, Google EGM, agent-skills |

## 2. 내가 겪은 실패별로, 다른 도구는 어떻게 푸는가

### 중복 개발 — 이미 있는 것을 못 찾아 새로 만든다

- **ponytail** (193k): 새로 쓰기 전에 사다리를 내려간다. ① 이 저장소에 이미 있는 것 ② 언어 기본 기능 ③ 브라우저·DB가 원래 해 주는 것 ④ 이미 깔린 라이브러리. 날짜 고르기를 요청하면 335줄을 새로 짜는 대신, 이미 있는 입력 부품을 찾아 쓴다. 단, 검증·오류 처리·보안·접근성은 줄이지 않는다. 핵심은 프롬프트 한 장이고, 그것을 대화 시작 때 넣어 주는 훅이 같이 들어 있다(처음에 "한 장이 전부"라고 적었던 것을 저장소를 다시 보고 고쳤다).
- **gstack** (141k): 같은 사다리("Search Before Building")가 모든 스킬 앞머리에 들어 있다. 검토 때는 "같은 일을 하는 코드가 두 군데 이상 있는가"를 따로 본다.
- **GSD** (64k): 계획 전에, 새로 만들 파일마다 "가장 닮은 기존 파일"을 찾아 그 파일의 방식(불러오기, 권한 확인, 오류 처리, 입력 검사)을 뽑아 적는다. 닮은 것이 없으면 "없음"이라고 적는다.

### 기존 프로젝트의 디자인·규칙을 안 따른다

- **agent-os** (5k): 코드에서 규칙을 한 번 뽑아 문서로 두고, 지금 만드는 것과 관련된 규칙만 골라 넣어 준다.
- **Trellis** (15k): 규칙을 `.trellis/spec/`에 두고 대화마다 관련된 것을 자동으로 넣는다. 일이 끝나면 새로 배운 규칙을 거기에 되돌려 적는다.
- **DESIGN.md** (awesome-design-md 127k, Google Stitch가 낸 개념): 화면의 색·글꼴·간격·부품 규칙을 글 파일 하나로 적어 두면 AI가 그것을 읽고 같은 모양으로 만든다.
- **impeccable** (112k): 처음 한 번 코드를 읽고 제품 설명 파일을 만든 뒤, 62가지 정해진 규칙으로 "AI가 만든 티"를 기계적으로 잡는다. AI 없이 도는 검사다.

### 코드 지도가 프론트를 놓친다

- **graphify** (149k), **Understand-Anything** (93k), **code-review-graph** (32k), **Trail-Code** (11k), **serena** (31k), **codebase-memory-mcp** (48k): 모두 함수·클래스·호출 관계를 그린다. "이 변경이 무엇을 깨뜨릴 수 있는가"까지 알려 주는 것도 있다(code-review-graph, Trail-Code).
- 그러나 화면 쪽(JSP, CSS, 화면에 딸린 스크립트)을 제대로 그리는 것은 찾지 못했다. 앞서 codebase-memory-mcp를 실제로 돌렸을 때도 JSP 4,854개 중 0개를 읽었다. **이 자리는 비어 있고, devkit의 화면 지도가 맡을 자리다.**

### 질문에 답하기 어렵다

- **mattpocock/skills** (326k): 사실은 AI가 직접 찾고, 사람에게는 결정만 묻는다. 질문마다 권하는 답을 붙여 "네"라고만 해도 넘어가게 한다. 사람이 답할 수 없으면, 답할 수 있는 사람에게 보낼 질문지를 만들어 준다. 못 알아들으면 쉬운 말로 다시 설명하는 스킬이 따로 있다.
- **agent-skills** (118k): 한 번에 하나씩, 짐작한 답을 붙여 묻고, 95%쯤 확신이 서면 멈춘다.
- **OpenSpec** (75k): 묻기 전에 코드를 먼저 보고 "이 프로젝트에서는 이렇게 하는 것이 가장 깔끔하다"를 먼저 내놓는다.

### 테스트가 사용자 흐름을 따르지 않는다, 보안이 불안하다

- **gstack** `/qa`: 실제로 화면을 열어 써 보고 → 고치고 → 다시 써 본다. 고치기 전에 그 문제를 잡는 테스트부터 만든다.
- **GSD** 검증: "파일이 있다"로 끝내지 않고 "사용자가 ○○을 할 수 있다"에서 거꾸로 내려가며, 화면 → 서버 → DB가 실제로 이어져 있는지 본다. 껍데기만 만든 것을 여기서 잡는다.
- **OpenSpec**: 요구를 "~할 때 / ~하면 / ~된다" 꼴의 장면으로 적는다. 이 장면이 곧 확인할 목록이 된다.
- **cloudflare/security-audit-skill** (74k): 구조와 입력 지점을 먼저 그린다 → 빠진 곳 없이 훑는다 → 찾은 것마다 새 AI가 "틀렸음"을 증명해 본다 → 살아남은 것만 보고한다.
- **gstack** `/cso`, **agent-skills** 보안 스킬: 무엇을 지켜야 하는지부터 정하고, "항상 한다 / 먼저 묻는다 / 절대 안 한다" 세 단으로 나눈다.

### 커진 뒤 관리가 안 된다

- **compound-engineering** (26k): 일 하나가 끝날 때마다 배운 것을 `docs/solutions/`에 적고, 다음 계획이 그것을 읽고 시작한다. "일을 할수록 다음 일이 쉬워져야 한다"가 구호다. 계획과 검토에 8, 만들기에 2를 쓴다.
- **Google EGM** (20k): 설계 문서와 지금 코드를 비교해 어긋난 곳을 알려 준다. 문서를 고칠지 코드를 고칠지는 사람이 정한다.
- **OpenSpec**: 변경이 끝나면 변경 기록을 보관함으로 옮기고 본 명세를 고친다. 명세가 늘 지금 상태를 가리킨다.
- **mattpocock**: 용어집을 대화 중에 바로 고친다. 결정 기록은 되돌리기 어렵고·뜻밖이고·실제로 저울질한 것만 남긴다. 한 대화보다 큰 일은 지도 한 장(목적지 / 지금까지 정한 것 / 아직 모르는 것 / 안 하는 것)으로 이어 간다. 같은 실수가 기계로 잡을 수 있는 것이면 규칙을 쓰지 말고 자동 검사를 만든다.
- **planning-with-files** (28k), **beads** (28k): 계획을 대화 안이 아니라 파일(또는 작은 DB)에 두고, 일 사이의 "이것이 끝나야 저것을 한다"를 기록한다.

### 순서대로만 가서 느리다

- **ccpm** (8k): 일을 쪼개 따로 떨어진 작업 폴더에서 여러 AI가 동시에 만든다.
- **oh-my-claudecode** (40k), **gastown** (18k), **orca** (127k): 여러 AI를 한꺼번에 굴리는 쪽이다. 따로 프로그램을 깔아야 한다.

## 3. 다른 도구들의 약한 곳

- **개발자를 전제로 한다.** 질문과 문서가 개발 용어다. 개발을 모르는 사람이 중대형 프로젝트에서 쓸 수 있게 만든 것은 찾지 못했다.
- **화면 쪽 지도가 없다.** 위에 적은 대로다.
- **새 프로젝트 쪽이 강하다.** 기존 코드에서 시작하는 길은 대부분 덧붙인 문서 한 장이다. (OpenSpec, BMAD, agent-os는 기존 코드를 앞에 내세운다.)
- **전부 덮으려면 여러 개를 깔아야 한다.** 과정 도구 + 지도 도구 + 디자인 도구 + 보안 도구 + 기억 도구.
- **너무 커진 것들이 있다.** ECC는 스킬 327개·에이전트 72개, wshobson/agents는 스킬 185개, gstack은 스킬 76개에 하나가 천 줄에 가깝다. 좋은 것을 볼 때마다 붙여 간 모양이고, mykit이 간 길과 같다. 반대편에 ponytail(프롬프트 한 장)과 mattpocock(7줄짜리 스킬)이 있고, 별 수는 이쪽이 더 많다.

## 4. devkit이 가져올 것

| 단계 | 가져올 것 | 어디서 |
|---|---|---|
| 받기 | 사실은 AI가 찾고 결정만 묻는다 · 질문마다 권하는 답 · 쉬운 말 · 답 못 하면 질문지 | mattpocock, agent-skills |
| 받기 | 요구를 "~할 때 ~하면 ~된다" 장면으로 적는다 (나중에 확인 목록이 된다) | OpenSpec |
| 찾기 | 다시 쓰기 사다리 · 새로 만들 것마다 가장 닮은 기존 것 찾기 | ponytail, gstack, GSD |
| 찾기 | 프로젝트 규칙·디자인 규칙을 한 번 뽑아 두고 관련된 것만 꺼내 쓴다 | agent-os, Trellis, DESIGN.md |
| 만들기 | 화면부터 DB까지 한 줄로 꿰는 작은 조각으로 쪼갠다 · 서로 안 기다리는 것은 동시에 | mattpocock, ccpm |
| 확인 | 실제로 써 보기 → 고치기 → 다시 써 보기 · 이어져 있는지 거꾸로 따라가기 | gstack, GSD |
| 검토 | 처음 보는 눈 · "요청대로인가"와 "이 프로젝트 방식대로인가"를 따로 본다 · 찾은 문제는 반증해 본다 | mattpocock, Google EGM, cloudflare |
| 검토 | 보안: 지킬 것 먼저 정하고 입력 지점을 빠짐없이 훑는다 | cloudflare, gstack, agent-skills |
| 마무리 | 배운 것 남기기 · 문서와 코드가 어긋났는지 보기 · 기계로 잡을 수 있는 실수는 자동 검사로 | compound-engineering, Google EGM, mattpocock |
| 전체 | 꼭 해야 하는 것은 자동 장치로 · 진행 상황은 파일에 · 일 크기에 맞춰 줄이기 | tdd-guard, planning-with-files, BMAD |

devkit만 하는 것: 화면까지 그리는 지도, 개발을 모르는 사람의 말, 기존 코드에서 시작하는 것을 기본으로 삼기, 한 번 설치.

가져오지 않는 것: 스킬 수백 개, 역할 수십 개, 따로 깔아야 하는 프로그램, 천 줄짜리 절차서.

## 받아 둔 원문

읽은 문서는 작업용 임시 폴더에 있어 PC를 다시 켜면 사라질 수 있다. 다시 필요하면 위 저장소 이름으로 GitHub에서 받는다.
라이선스는 대부분 MIT 또는 Apache-2.0이다. 글을 그대로 옮겨 쓸 때는 저장소별로 다시 확인한다 (karpathy-skills는 라이선스가 없어 옮겨 쓰지 않는다).
